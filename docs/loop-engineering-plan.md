# Canban 改善ループ — 設計と実装

2026-10-09 / v0.27.0 / `codex/loop-engineering-plan`。

## 採用した形

**中心に目標を置く「軌道シート」と、タスクカード内の改善ループを実装した。** ボードと同じ仕事を円と螺旋で読み、プロジェクトの大きな周期に小さな修正を紐付ける。全体のモード切り替えや別ページは作らない。

使う人が書くのは「できたと言える条件」「観測と根拠」「次の調整」。条件を設定し、1周の調整を開始し、検証を記録すると、次の調整・確認・停止へ進む。エージェントへの指示には前の観測が引き継がれ、送信は人が1回ずつ行う。

これは**ループを設計・運用する手動補助版**。検証コマンドの自動実行や、結果を読んで無人で次のターンを送る制御までは実装していない。原著が扱う自律的なLoop Engineeringの完成として宣伝しない。定義と一次資料は[調査ノート](loop-engineering-research.md)を参照する。「ほとんどの人がこの方式を使う」という普及率は確認できていない。

## 図が意味すること

| 図の要素 | 仕事での意味 |
|---|---|
| 中心 | 目標。守る原則と条件を文字でも示す |
| 外側の輪 | 大きな周期の、いま残っている未達と未観測の条件 |
| 小さな衛星 | 同じタスクに属する小さな修正ループ。親子は2段まで |
| 輪の半径 | 確認済み合格の割合から計算する。未観測と未確認の報告は合格にしない |
| 段階の位置 | 目標・実行/検証・調整・達成という現在の段階。物理的な時間軸ではない |
| 螺旋の線 | 同じ基準の版の中で記録・確認した周回。基準を変えたら線をつながない |
| 点線 | 現在の進みが未確認、または未観測が残る部分 |

条件の確認率は工数の消化率ではない。新しい問題を見つければ輪は広がる。目標に近づいたように見せるために輪を自動で縮めない。図と同じ数値・条件・根拠を文字と `progress` 要素でも読めるようにする。

## 実装した操作

1. タスク内で、目標・完了の条件・守る原則・周回上限を設定する。
2. 今回の調整を書く。大きな周期と小さな修正を選び、1周を開始する。
3. 必要なら、紐付いたCodex/Claudeセッションへ指示の下書きを編集して手動送信する。
4. 条件ごとに合格・未達・未観測、説明、根拠の参照を記録する。成果物の版と学びも残す。
5. エージェント報告はUIで確認する。すべての条件と子ループを確認したら達成。残っていれば次の調整へ進む。

同じ観測が2周続く、または周回上限に達すると停止する。確認操作だけでその停止を解除しない。基準と進め方を見直し、新しい版で続ける。履歴は削除しない。

## UIの配置

- 軌道シートは既存のレイヤー2。サイドバー「見る」の「軌道」、`Shift+O`、⌘Kから開閉する。アプリバーと背景のボードは残る。
- タスク内の改善ループへは `Shift+L` と⌘K。読み込み後に対象へスクロールし、フォーカスする。軌道シート内でも `Shift+L` は部品へ移動する。
- `v` は既存のSlack操作のため使用しない。キーの一覧と操作横のヒントを更新した。
- 入力途中の文章はローカルの下書きとして保持し、閉じる・親子の切り替え・再読み込みで復元する。
- ボードのカードには周回・状態・「前回の確認」を表示する。すべてのGit作業フォルダをボード更新のたびに走査しない。
- 0.26.xでレイアウトはTrelloの1種に統合済み。この実装はその共通部品に追加し、撤去済みの4種を復活させていない。

## データと実行の契約

| 部分 | 実装 |
|---|---|
| 状態・基準の版 | `loop_state`。操作IDとrevisionで再送・競合を扱う |
| 周回・観測・根拠 | `loop_rounds`。終了した周回は変更できず、ボード全体を書き直さない |
| 手動送信 | `loop_dispatch`。1周回1依頼をSQLiteのトランザクションで結ぶ |
| 送信直前 | claimの時点で周回・基準・状態・紐付けを再照合。無効な待機依頼は取消 |
| 親の達成 | 子が達成した後の親の新しい検証が必要。子の変更・再検証・完了で親の進みを未確認に戻す |
| 成果物の版 | ローカルGitはHEAD、差分、未追跡ファイルを指紋化。観測後の変更を未確認とする |
| 手入力の版 | Git以外・リモート・照合不能時は明示する。人が参照を確認し、変更を自動検出できるとは表示しない |

ローカルGitの照合は無制限の走査ではない。コマンドは3秒、差分/読み取りは4MiB、未追跡ファイルは100件まで。Gitで無視したファイル、外部サービスの状態、実際のテストログの真偽は自動検証しない。

UI確認とエージェント報告をサーバーでも区別する。確認・ループ送信は起動ごとのUI能力トークンを必要とし、ChromeはNative Messagingの経路で付与する。トークンはサーバー起動時に環境変数から消し、dispatchでも除去し、監督されるCLIに継承させない。**この境界はUI経路の確認であり、人間本人の認証ではない。** MCP Appsのリソースを意図的に読むクライアントや同じOS権限の任意コードはUI能力を取得し得る。悪意あるローカルコードからの保護には使わない。

一時停止は次の待機依頼を取り消す。claim済みの開始処理・実行中CLIを強制停止する保証はなく、既存の依頼一覧で停止する。通常の権限・実行中・入力待ちの判定は既存dispatchを使う。

## 他の可視化案との比較

| 自然・道具からの案 | 見える関係 | 適する用途・注意点 |
|---|---|---|
| 惑星と衛星 | 大周期と小周期、中心の目標 | 今回採用。衛星は親子関係を表す |
| 渦・螺旋 | 周回ごとの変化と収束 | 今回の履歴に採用。後退も描く |
| 年輪 | 基準ごとの履歴の積み重ね | 学びの振り返り。現在の距離とは分ける |
| 河川と支流 | 並行作業が目標へ合流 | 複数担当の合流。反復は補助表示が必要 |
| 樹木と枝 | 目標の分解、依存の階層 | 計画の整理。循環は見えにくい |
| 波と振り子 | 周期と位相、待ちのずれ | チームのテンポ。成果との距離は別の軸 |
| 蜂の巣 | 条件や領域の隣接と担当 | 網羅性。固定マスを強制しない |
| 呼吸 | 実行と観測の交代 | 初心者への案内。長期履歴の一覧には弱い |
| 時計と文字盤 | 段階、周期、停止 | 今日の操作。時間と進捗を混同しやすい |
| 航海計器・羅針盤 | 目標からのずれと次の修正 | 状態監視。表示する尺度の定義が必要 |
| ミキサー・調整卓 | 並行する小さな制御と結果 | 性能や品質の調整。一般タスクには複雑 |
| 看板とカード | 担当、状態、待ちの一覧 | 既存ボードとして維持。周期は軌道シートで補う |

## 次の実装段階

1. **今回完了:** 版付き基準、大小2段、軌道/カードUI、観測/学び、手動1ターン送信、停止条件、回帰試験。
2. **今後:** 根拠の型（コマンド/CI/画面確認）と取得経路、同じ条件での自動検証、成果物の範囲、費用・時間の予算を定義する。
3. **その後:** 取得した根拠から次のターンか停止を決める範囲付き自動制御。人への引き渡し、故障時の再開、予算の強制、停止の実効性を先に検証する。

マンダラの固定8枠、任意カード間の依存グラフ、無人の自動反復は今回の提供範囲に含まれない。
