## 2. 実操作で分かったこと

### 2.1 うまくいっていること（守る）

- 時間軸は、ハーネスを選ばずに 要対応→実行中→昨日→今週 と並び、右に同じカードがドッキングする。R1 の骨格はすでにある（[02](evidence/02-timeline-waiting-light.jpg)）。
- AI App と利用面のバッジ（`Claude CLI`、`Antigravity IDE`）は行とカードで一貫している。
- Antigravity の `task.md` から計画の進み（1/3）が出る。
- 寿命による密度と「休眠中 N」の折りたたみは、量に耐える。
- 承認を Canban から行わせない契約は、R8 そのもの。

### 2.2 一続きの体験を切っているもの

1. **入口がボード**。カテゴリもリストも使っていない状態では、9件が「受信箱」に縦に並び、右3列は空（[01](evidence/01-board-light.jpg)）。看板は「分類してから使う」道具で、分類の負担が先に来る。
2. **待ちの中身が読めない**。Claude の質問待ちを開いても、質問文「Luhn 検証を入れますか？」はどこにも出ず、「ツールを1件使用」と「アプリで答えてください」だけ。何を聞かれているか知るために元アプリへ行く必要がある。
3. **同じ仕事が3行に散る**。「決済フォーム」の Claude CLI・Codex CLI・Antigravity IDE の3セッション（同じ作業フォルダー、うち2件は同じブランチ）が、要対応・実行中・今週に分かれて並び、関係を示すものがない。
4. **続ける操作が遠い**。詳細パネルを開くと会話の幅は約265pxまで狭まり、「再開」は下端の外（[04](evidence/04-timeline-long-details-light.jpg)）。
5. **探し直せない**。⌘K に「決済」と打つと3件出るが、アーカイブ済みの「決済フォームの設計メモ」は出ない。結果の行は色の点だけで、どのアプリのセッションか読めない（[05](evidence/05-palette-search-light.jpg)）。
6. **長会話**。220往復の会話で「思考・実行ステップ」の列が会話の全発言を複製して並べる。目次としては長すぎ、幅を160px使う。第一段階では触らないが記録する。
7. **サイドバー**は約50項目。絞り込み・元アプリ・作業フォルダー・ラベル・dot・表示対象・見る・管理が1列に並ぶ（[06](evidence/06-timeline-archived-dark.jpg)）。「全体を一緒に見て必要なときに分ける」ためには多い。第一段階では増やさないことだけ決める。

### 2.3 ガントは観測していない値を描いている

`ui/gantt.js` を読み、画面でも確認した（[03](evidence/03-gantt-light.jpg)）。

- 進捗は固定値。タスクは常に 75%、セッションは実行中 80%・その他 50%。`card.status === 'done'` という存在しない状態も参照している。
- 帯の位置と幅は `updatedAt` だけから作られ、最小96px。開始は観測値ではなく、右端は今日の線を越えて未来へ伸びる。
- ホバーの説明は、活動がなければ「タスクが進行中です」を出す。
- 行に AI App の印がなく、入力待ちが色でも文字でも区別できない。
- ライトテーマでも濃紺の面で描かれる。
- `i` は ボード→時間軸→ガント と3つを巡回するが、共有UI状態の復元（`ui/boot.js`）は board／timeline しか受け付けない。
- AGENTS.md と docs/ui-components.md にガントの記載がなく、試験もない。

brief の「予定のない仕事に架空の日程を付けない」「取得不能を正常と見せない」に反する。ローカル main の `c6d1ed7`（0.29.73、未push）がトークンと切替を直しているようだが、こちらでは画面を確認していない。

### 2.4 要確認の観測

- 架空データで Codex の `source: 'vscode'` のスレッドが `CLI` と表示された。`inferSurface()` は Codex の `source`／`threadSource` を見ていない。実機の Codex Desktop が書く値をこちらでは確認できないため、誤表示かどうかは未確定。「今日はCLI、今日はデスクトップ」を扱う以上、バッジの正しさは U1 で確かめる。
- ローカル main の `df81b75`「同名既存カテゴリへの自動合流」は、0.29.28 で固定した「名前一致で結合しない」（[概念対応](../agent-concept-mapping.md)）と、brief の「同名でも別の仕事」に反する可能性がある。読んだのはコミット名だけ。移植の前に人間の確認が要る（§10）。

3つは別の能力として扱い、画面でも別の言葉にする。下表はソースと既存設計から読んだ範囲で、実機の到達は未確認。

| 対象 | 一覧に見える | 会話を読む | アーカイブ済み | 元アプリで開く | Canban から追加依頼 |
|---|---|---|---|---|---|
| Codex CLI / Desktop（このマシン） | ○ 状態DB | ○ rollout | ○ 取得・操作とも可（App Server） | Desktop リンク／CLI 再開 | ○ CLIで1ターン |
| Codex Cloud（dot） | ○ 保存済みキャッシュ | × 元アプリで読む | 未取得 | Codex を開くだけ | × |
| Claude CLI | ○ transcript | ○ | Desktop メタデータがある場合だけ分かる | CLI 再開 | ○ |
| Claude Desktop | ○ | ○ | ○ 取得のみ。操作は未対応 | セッションIDとアカウントが一致するときだけ正確に開く。他は同じフォルダーで新規 | ○ |
| Antigravity（IDE／Brain） | ○ 読み取り専用 | ○ | 終了扱いの印のみ | `antigravity://conversation/…`（到達は未確認） | × |

- **別ハーネスで続行**は「同じ会話の移動」ではない。どのハーネスも他社の会話を取り込む公式経路を持たないため、Canban でできるのは「同じ仕事に、新しいセッションを別の AI App で始める」こと。引き継ぐのは人が確認して送る依頼文で、会話履歴そのものではない。画面でもそう書く（§5.4）。
- 取得できない値は `Observation.status`（known／absent／unknown／unavailable／stale）をそのまま言葉にする。「アーカイブ済みか不明」を「アーカイブなし」にしない。

## 4. 共通ドメイン

### 4.1 人が区別したいのは4つ

名詞を増やす前に、何を区別したいのかを並べる。

| 人の問い | Canban の語 | 所有者 | 寿命 |
|---|---|---|---|
| これは**どの仕事**か | タスクカード（＝仕事1件） | Canban | 仕事が終わるまで |
| **どの領域**の仕事か | カテゴリ（1つ）／ラベル（複数） | Canban | 長い |
| 元アプリでは**どこにあった**か | 元アプリの属性（Codexのプロジェクト、Claudeの環境 等） | 元アプリ | 元アプリ次第 |
| **どこで動いた**か | 作業フォルダー、ブランチ、マシン | 実体 | セッションごと |

結論: **新しい抽象名は作らない。** 「Canban 共通の仕事をまとめる概念」は既存のタスクカードが担う。CONTEXT.md の定義（「Canbanで管理する仕事と完了条件」）と H1（1タスク＝1カード）が一致している。足りないのは概念ではなく、まとめる操作の軽さと、まとまった姿の見え方。

- 各ハーネスの「プロジェクト」は統合しない（0.29.28 の契約を維持）。同名でも `SourceRef` が違えば別物、別名でも人がまとめれば同じ仕事。
- 自動推定は**候補の提示まで**。紐付けは人の操作でだけ起き、根拠（「同じ作業フォルダーとブランチ」）を候補に添える。人がまとめた／外した結果は推定で上書きしない。
- 既存の例外（Canban から開始したセッションの自動紐付け）は、人が開始を押した結果なので維持する。

### 4.2 1つの仕事と複数セッション

- タスクカード 1 ─ N セッション（既存 `links`）。1セッションは1タスクにだけ属する（既存の制約）。
- タスクの「状態」は紐付いたセッションの状態の集約であり、仕事の完了ではない（既存の表記「リンクしたセッションの状態」を維持）。
- 紐付いていないセッションは、そのまま1行の仕事として扱う。まとめることを強制しない。

### 4.3 関係の型（第二段階の入口）

カード同士の関係は3つを区別する。第一段階では保存も表示もしない。型だけ決めておく。

| 型 | 意味 | 向き | 表示の位置（案） |
|---|---|---|---|
| `derived` 派生 | この仕事から生まれた別の仕事（親子） | 親→子 | 親の中に入れ子 |
| `blocks` 依存 | これが終わらないと進めない | 先→後 | 行の印と、工程表の線 |
| `ref` 参考 | 読むと役に立つだけ | 無向 | 詳細の「関連」 |

セッション間のやり取り（0.27.13）とサブエージェントの親子は「観測した事実」で、上の3つは「人が付けた意味」。同じ表に混ぜない。

## 5. 案の比較と推奨

| | A. 時間軸を主画面に育てる | B. 看板のまま所属を解く | C. 工程表／キャンバスへ全面刷新 |
|---|---|---|---|
| 中身 | 既存の時間軸に、待ちの中身・仕事のまとまり・続ける・探し直すを足す | レーンとカテゴリを強化し、ボードで全体を見る | 新しい主画面を作り、ガントや線で関係を描く |
| R1〜R6 | 6つとも既存部品の延長で届く | R1・R2 は届くが、分類が先に必要なまま | R6 は強いが、R1〜R5 を作り直すことになる |
| 人の負担 | 整理しなくても使える。まとめるのは任意 | 分類を人に戻す。brief の「使いこなせない」が残る | 予定・依存を入力しないと空の工程表になる |
| 既存との重複 | なし（部品を直す） | なし | ボード・時間軸・ガントに重なる |
| 規模 | 小〜中。5つの独立した単位 | 中 | 大 |
| 危険 | 「Trello を基調」と入口が食い違う（§7） | 現状維持に近い | 架空の日程を描く圧力が増す |

**推奨は A。** 理由は3つ。実操作で一番使えたのが時間軸だった。brief の経路（見つける→待ちを理解→読む→続行→探し直す→まとめる）がそのまま時間軸の上から下、左から右に載る。新しい画面も名詞も増やさずに済む。

B は捨てない。ボードは「段階を自分で動かしたい仕事」の補助表示として残す。C のうち、関係の型（§4.3）と誠実な活動の帯（U5）だけを先に取り込む。

## 6. 主画面と操作経路（第一段階）

主画面は時間軸。左が仕事の一覧、右が選んだカード。[prototype.html](prototype.html) に架空データの静的な試作を置いた（ライト／ダーク）。

```
┌ アプリバー（既存のまま）──────────────────────────────────────────┐
├ 時間の帯（既存のまま）────────────────────────────────────────────┤
│ 一覧                         │ 選んだカード（既存のスレッド詳細）      │
│ 要対応 1                     │ 決済フォーム: カード番号検証            │
│ ▸ 決済フォーム        3      │ Claude CLI · 入力待ち   [ターミナルで再開 o ▾] │
│   ● Claude CLI   質問: Luhn… │ ─────────────────────────────── │
│   ◐ Antigravity IDE  1/3     │ 会話                                    │
│   ○ Codex CLI    3日前       │ …                                       │
│ 実行中 1                     │ 質問: Luhn 検証を入れますか？           │
│ ◐ ログイン修正  Codex CLI    │   はい / いいえ （元アプリで答える）    │
│ 昨日 2 …                     │ 入力欄                                  │
└──────────────────────────────┴─────────────────────────────────┘
```

経路ごとの変更点。番号は実装単位（U1〜U5）。

### 6.1 見つける・待ちを理解する（U1）

- 要対応・実行中の行に2行目を足す。入力待ちは「質問: 本文」「計画の確認待ち」「許可待ち」、中断は「中断」、実行中はいまの動き（既存 `activity`）。それ以外の行は1行のまま（密度は寿命が決める、を守る）。
- 質問文が取れないときは種類だけを出す（「質問への回答待ち」）。本文を作らない。
- タスクカードの行は、紐付いたセッションを入れ子で並べる（状態の記号、AI App・利用面、2行目）。置く場所は一番急ぐ子の区分（既存 `taskLifeStatus`）。子は3件まで、残りは「ほか N」。
- ドッキングしたカードの入力欄の上に、質問文と選択肢を読める形で出す。答えは元アプリで行う（承認ボタンは置かない）。

### 6.2 続ける（U2）

- 「再開」の主ボタンを、詳細パネルからスレッド詳細の見出し（`.th-head`）へ移す。キーは既存の `o`。入口は1か所のまま、場所だけ近づける。
- ボタンの文言で経路を言い切る: 「Claude で開く」「ターミナルで再開」「Antigravity で開く」。正確に同じ会話へ届かない場合は「同じフォルダーで新しく開く」と書く。
- 使えないときは無効にして理由を出す（`capabilities.open` の `blocked`／`unknown`／`unsupported`）。
- ▾ で経路の選択（デスクトップ／ターミナル、表示先）。アカウントや接続の設定は詳細パネルに残す。

### 6.3 まとめる（U3）

- 選んだセッションで `x`（仮）、または⌘K「仕事にまとめる」。レイヤー4のピッカーが開く。
- 上から「候補（根拠つき）」「新しいタスクカードにまとめる: 〈セッション名〉」「すべてのタスクカード（入力で絞る）」。
- 候補は、同じマシン・同じ作業フォルダー・同じブランチのセッションを持つタスクカード、次に同じフォルダーだけ一致するもの。根拠を1行で添える。候補は提示だけで、自動では紐付けない。
- 実行後は「まとめました · 取り消す」。取り消しは紐付けを外し、この操作で作ったタスクカードで未編集なら削除する。
- 詳細パネルの「タスクカード」の選択は、同じピッカーを開く行に置き換える（部品を1つにする）。

### 6.4 探し直す（U4）

- ⌘K のカード検索に「ボードの外」の区分を足し、アーカイブ済みと表示期間の外のセッションをサーバー検索で探す。行に AI App・利用面と「アーカイブ済み」「30日より前」を文字で出す。
- タイトルなどの検索は取得済みの全セッションが対象（既存 `canban_search`、期間なし）。本文検索の索引は直近90日なので、本文で探すときはその限界を区分の末尾に書く。
- 「アーカイブ済みも表示」で出た行とカードに、アーカイブの印を付ける。アーカイブ状態が取れないセッションは印を付けない（不明を「なし」にしない点は詳細の元アプリ欄で示す）。

### 6.5 流れを見る（U5）

- ガントを観測値だけで描き直す。帯は「最初の記録から最後の動きまで」。進捗の％は出さない。今日より右へは伸ばさない。期限があるカードだけ期限の印を出す。
- タスクの行は、子の帯を包む枠。子の行に AI App・利用面と状態。
- 凡例を1行置く: 「帯は観測した活動の期間です。予定ではありません」。
- 予定・依存を入力して工程表にするのは第二段階（§4.3 の `blocks`）。

## 7. 旧 AGENTS（Trello 前提）との衝突

| AGENTS の原則 | 今回の方針との関係 | 判断 |
|---|---|---|
| 見た目と画面構成は Trello を基調にする | 主画面を時間軸に寄せる | **見直す前提。** ただし第一段階では既定の表示を変えない。変えるかは人間に確認（§10-Q1） |
| ページはボード1枚。新しいページ・ルートを足さない | 時間軸もガントも同じページの別の並べ方 | 守る。新しい画面は作らない |
| 入口は1か所 | 「再開」の移動、「タスクカード」選択の置換 | 守る。移す・置き換えるだけで増やさない |
| 密度は寿命が決める | 要対応・実行中だけ2行 | 守る。設定を足さない |
| 新しい「時間」の機能は寿命・時間の帯・時間軸に載せる | ガントはこの原則の外で追加された | 文書の欠落。U5 で ui-components.md に受け持ちを書く |
| Canban は許可待ちに答えない | 質問文を読めるようにするが、答えは元アプリ | 守る |
| 新しい操作にはキーと⌘K | `x`、「仕事にまとめる」 | 守る |
| 5配置で共通の部品 | 変更は共通部品（行、スレッド見出し、ピッカー） | 守る。5配置での確認が要る |
| リスト・カードの見た目（灰色・272px 等） | 触らない | 守る |

守る価値があるのは「ページを増やさない」「入口は1か所」「設定を増やさない」「勝手に実行しない」。見直すのは「看板が入口である」という1点だけ。

## 8. 第一段階と後回し

**第一段階（U1〜U5、各1PR）**: 待ちが読める行と仕事の入れ子／続けるを見出しへ／まとめる／探し直す／ガントの誠実化。順番と受け入れ条件は [implementation-spec.md](implementation-spec.md)。

**後回し**

- 既定の表示を時間軸にする（Q1 の回答後）。
- 別の AI App で続ける（仕事に新しいセッションを開始し、引き継ぎ文の下書きを入れる。送信は人）。U3 が入ってから。
- カード間の関係（派生・依存・参考）の保存と表示、依存を持つ工程表、ホワイトボード。
- 長会話の「思考・実行ステップ」の目次化、サイドバーの整理。
- 元アプリ側のアーカイブ・ピンとの連動。

## 9. 状態モデル

内部キーは変えない（0.29.28 の契約）。行と見出しの言葉だけ揃える。

| 状態 | 一覧の区分 | 行の2行目 | 続ける |
|---|---|---|---|
| 実行中 `running` | 実行中 | いまの動き | 開ける。追加依頼は不可（既存） |
| 入力待ち `waiting` | 要対応 | 質問: 本文／計画の確認待ち／許可待ち | 「元アプリで答える」を主にする |
| 中断 `aborted` | 要対応 | 中断 | 開ける |
| 応答済み `completed` | 日付 | なし | 開ける |
| 待機中 `idle` | 日付 | なし | 開ける |
| 状態未取得 `statusKnown:false` | 日付 | 「状態は未取得」 | 能力が `unknown` なら理由つきで無効 |
| アーカイブ済み | 表示対象に含めたときだけ。印つき | なし | 経路があれば開ける。なければ理由 |
| 取得不能（ソースの読み取り失敗） | 既存の警告（アプリバーの △）を維持 | — | — |

## 10. 人間への確認（根本的なものだけ）

Codex は Q の回答を待たずに U1〜U5 を始められる。どれも既定の表示とデータを変えない。

- **Q1 入口を時間軸にするか。** 推奨は「表示の保存値がない人だけ時間軸で開く。保存済みの人は変えない」。AGENTS の冒頭（Trello を基調）を書き換えることになる。U1〜U4 を使ってから決めてよい。
- **Q2 「同名カテゴリへの自動合流」（ローカル main `df81b75`）を残すか。** brief の「同名でも別の仕事」と 0.29.28 の契約に合わせるなら、自動合流は候補の提示に留めるのが筋。このブランチへは移植せず、判断を待つことを勧める。
- **Q3 ガントの名前。** 中身を観測した活動の帯に直すと「ガント」は予定表を連想させる。推奨は第一段階では名前を変えず凡例で補い、依存と期限が入る第二段階で決める。
