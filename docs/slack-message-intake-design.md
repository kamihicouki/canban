# Slackメッセージの取り込み設計

状態: 設計インタビュー中。機能の実装・Slackへの接続は未着手。
最終更新: 2026-10-06

## 確定した要件

- Slackの依頼を拾って対応漏れを防ぎ、会話を材料として仕事を整理し、エージェントに渡せるようにする。
- ボード内にSlackタイムラインを表示する。リスト形式かどうかは固定せず、Slack由来と分かり、簡単に非表示にできることを優先する。
- 非表示にするのはタイムラインだけ。取り込んだタスクカードは表示対象として残る。
- 複数のSlackワークスペースに接続できる。
- 公開・非公開チャンネル、DM、グループDMを対象にし、本人がアクセスできる範囲から読む会話を選ぶ。
- 特定のメッセージ1件を起点に、既存の種類であるタスクカードを作る。2件目以降はあとから追加できる。
- 新規作成は即時確定せず、タイトル・カテゴリ・取り込み先リストを編集してから作成する。
- タイムラインからスレッドの返信も読める。返信1件を選んでカード作成・追加できる。
- 既存のタスクカード・セッションカードの両方にSlackメッセージを紐づけられる。
- 同じSlackメッセージを複数のカードに紐づけられる。
- 履歴の保存対象はカードに紐づけたメッセージだけ。タイムライン全体の変更履歴は保存しない。
- 対象メッセージの変更は、履歴として取り込む。Canbanが取得・受信できなかった変更の完全な復元は保証できない。
- Slack側で削除された後も、保存済みの本文を履歴に残す。
- 取り込み済みのメッセージは、関連カードの表示付きでタイムラインに残す。
- 初期はSlackに対して読み取り専用とし、返信・リアクション・Slack側の既読反映は行わない。
- 初期の導入対象は本人の個人利用。一般のCanban利用者向けの接続・配布は初期範囲に含めない。
- チャンネルやDMは、任意の既存カテゴリに対応付ける。複数の会話を同じカテゴリにまとめられる。
- 対応先のカテゴリがなければ追加できる。未分類も許可する。

## 次に決めること

- 同期の稼働期間と、タイムラインを非表示にしたとき・Canbanを閉じたときの動作。
- 履歴に記録した変更と、カードの説明・エージェントに渡す本文の関係。
- 本文以外の添付ファイルを初期範囲に含めるか。
- 初回の過去メッセージ取得範囲、紐づけ前のタイムラインのキャッシュ、最後の参照を外した後の記録保持。
- エージェントへ渡す内容と実行開始の操作。
- 表示形式、復帰操作と表示状態の保存、Canban内の確認済み状態。
- タイトル・説明の初期値、カテゴリの既定値と手動変更、同じカードへの二重追加防止。
- レイヤー、キー、5レイアウトの操作経路、検証と導入の条件。

## 実装への接続案

ここでは既存コードから決められる接続先を記す。同期の稼働期間や、エージェントへ渡す内容などの未決事項を確定してから実装する。

- 保存先は既存のCanban保存先を使う。通常利用は `~/.canban/`、開発・テストは明示した `.local/` 配下とし、別の実データを作らない。
- 複数クライアントのサーバーは同じSQLiteを使う。Slackの取得・イベント受信は、既存のリーダー制御に接続し、複数プロセスで重複実行しない。既存の背景処理は全サーバーの終了とともに止まるため、常駐運用の有無は別途決める。
- `task.context` は所属情報、`links` はエージェントのセッション紐づけとして維持する。Slack参照と履歴には別の保存・API・表示モデルを用意する。
- 新規カードの作成にはタスク追加ダイアログを使い、作成と最初のSlack参照の追加を一体で行う。同じカード・同じメッセージの二重追加を防ぐ。同じメッセージを別カードへ追加する操作は許可する。
- Slackの接続・対象の会話・カテゴリ対応は管理パネルに置く。タイムラインはボード面、カードのSlack資料はカードオーバーレイ内に置く。タイムラインはまず選択した会話を1列にまとめ、各メッセージにワークスペースと会話名を示す。
- タイムラインの表示状態は共有UI状態へ保存する。表示操作を各レイアウトの唯一のナビゲーション経路へつなぎ、キーと⌘Kも用意する。キーは実装時に全ハンドラと照合する。
- 既存の新規セッション開始はタイトル・説明・メモを依頼文の初期値にし、既存セッションへの送信は指定した依頼文を使う。Slack参照は現在、自動ではどちらの依頼文にも含まれない。添付する本文の版・範囲と送信操作を決め、既存の20,000文字の上限を保つ。
- 認証情報はGit管理外に置き、ボードのデータ応答や配布物に含めない。個人利用向けのSlackアプリと読み取り権限を前提に、ローカル接続の手順を用意する。実際のアプリ導入・権限付与は別途行う。

## 検証の範囲

- メッセージ・返信の取り込み、既存タスク・セッションへの追加、多対多の参照、二重追加防止、編集・削除の履歴を検証する。
- 未取得期間の扱い、再接続、リーダー交代、API制限・権限不足と部分取得を検証する。取得できないことだけで削除と判断しない。
- 隔離した `.local/` のデータで `npm test` を実行する。認証情報や実際のSlack会話はテスト資料に使わない。
- 1280×800で5レイアウトのライト・ダークを撮影し、表示の開閉、カード作成、スレッド閲覧、履歴表示、Esc・キー・⌘Kを確認する。
- 本人のSlackへの実接続、ローカルmainへの取り込み・登録済み拡張の更新、Chrome Web Store申請はそれぞれ別の工程とする。現在はいずれも未実施。

## インタビューの判断順序

- 解決したい仕事 → 新規カード作成・既存カードへの紐づけ → 取り込み先と作成内容 → エージェントへ渡す内容。
- ボード内で読む → Slack由来の識別と簡単な非表示 → 表示形式・非表示対象 → フィルターと保存状態。
- 複数ワークスペース → 対象の会話を選択 → 認証と取得方法 → 更新頻度・切断時の動作。
- カテゴリへの任意対応 → カテゴリの作成・未分類 → 対応変更時の既存カードの扱い。
- メッセージを複数カードへ紐づけ → 同一カードへの重複防止 → 紐づけ解除と参照の保持。
- 変更を履歴に記録 → APIで取得できる範囲の確認 → 保持・削除と、カード本文・エージェントへの反映。
- Slackへの読み取り専用接続 → 閲覧・取り込みの操作 → Canban内の確認済み状態。

## 既存モデルとの接点

- カテゴリとカードの配置先リストは別の軸。現在、カードのカテゴリは1つで、未分類もある。
- 現在のタスクカードはタイトル・説明・カテゴリ・ラベル・リストを持つ。Slackの元メッセージを識別する専用属性はない。
- 既存のカードのセッション紐づけと、Slackメッセージの参照は意味が異なる。
- 2026-10-06のコード調査ではSlack連携は見つからなかった。
- ボード以外のページは増やさず、接続などの管理は既存の管理パネルの契約に従う。

## 履歴の取得範囲に関する事実

2026-10-06にSlack公式資料を確認した。以下は取得方法や保存方針の決定ではなく、実現可能な範囲の制約である。

- [message_changed](https://docs.slack.dev/reference/events/message/message_changed/)は更新されたメッセージを通知する。取得・受信できた版を記録する材料になる。
- [message_deleted](https://docs.slack.dev/reference/events/message/message_deleted/)では、元のメッセージは以後の履歴取得に返らないと明記されている。未取得のまま削除された本文は、履歴の再取得だけでは復元できない。
- [Events API](https://docs.slack.dev/apis/events-api/)はbest-effortの配信で、全変更の受信を保証しない。[Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)にも、接続を確立するまでイベントを失う可能性が記載されている。
- [conversations.history](https://docs.slack.dev/reference/methods/conversations.history/)は現在取得できるメッセージを返すAPIで、全ての過去の編集版を取得する契約はない。
- したがって、初回接続前や停止中の中間の編集・削除を全て復元するとは約束しない。再取得による本文の差分と、実際に受信した編集・削除イベントを区別する必要がある。
- メッセージが再取得できないことだけでは、削除・アクセス権の変更・Slack側の保持期間による消失を区別できない。

## 接続・配布方式を決めるための事実

- [ユーザートークン](https://docs.slack.dev/authentication/tokens/)と読み取り権限による取得が、本人のチャンネル・DMを対象にする用途に適する。botトークンはbot自身がアクセスできる会話が対象で、人同士のDMを本人に代わって読む範囲とは異なる。
- [OAuth](https://docs.slack.dev/authentication/installing-with-oauth/)ではユーザーの読み取り権限を要求できる。必要な会話の種類に応じて権限を選ぶ。初期範囲にはSlackへの書き込み権限を要求しない。
- [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)は公開HTTPエンドポイントなしでイベントを受信でき、ローカル常駐プロセスでも利用できる。一方、app-levelトークン、接続更新、再接続、ACKが必要で、アプリ単位の同時接続数は10まで。イベントは複数接続の全てに配信されるものではない。共通Slackアプリに各利用者の端末を直接接続する一般配布方式には制約がある。
- Socket Modeのアプリは現在、公開Slack Marketplaceへの掲載が許可されていない。
- [取得制限](https://docs.slack.dev/apis/web-api/rate-limits/)はアプリの配布区分に依存する。新規のMarketplace外商用配布アプリでは、`conversations.history`と`conversations.replies`が各1リクエスト/分・最大15件となる。Marketplace掲載アプリと社内自作アプリはTier 3。個人・社内向けか一般配布向けかを決めてから、取得・接続方式を選ぶ。
