# タスク作成のゴール契約 — 設計書（A+B+C）

2026-11-08 / 対象: 0.30 系 / 状態: 設計（未実装）

## 目的

作成ダイアログの「タスクカード」は、タイトルと説明の自由入力だけで作る。エージェントに自走させる仕事では、人が最初に決めるべきこと（完了の条件、確かめ方、予算、人の関門）が書かれないまま着手され、カードの中で後から改善ループを設定し直している。

この設計では、タスクを**作る時点**で「どこまで任せるか」を選び、その度合いに必要な属性を案内し、足りないまま着手しないようにする。

- **A. ゴールの契約**: 作成ダイアログに目標・完了の条件・確かめ方・範囲・予算・関門を置き、既存の改善ループ（`server/loop.mjs`）をカード作成と同時に設定する。
- **B. 任せる度合い**: L0〜L2 を選び、度合いに応じて必須の項目を増やす。
- **C. 着手の準備度**: 契約の充足をカードの表面に示し、着手（実行列への移動、エージェントへの送信、周回の開始）の前に足りない項目を示す。

対象外: 書いたメモをエージェントが契約に整える案（D）、大きなゴールのグラフ分解（E）、検証コマンドの自動実行。L3 は E のために番号だけ予約する。

## 背景（調査の要点）

公開されている実践（Loop / Graph engineering、Spec Kit・Kiro の仕様駆動、Claude Code・Codex の `/goal`）では、人は「確かめられる完了の条件」「止める条件と予算」「人が判断する関門」を先に決め、エージェントは実行・検証・次の一手を繰り返す。ループが閉じない主な原因は、エージェントが自分で確かめられない条件（例:「PRがレビューに通る」）である。出典の多くは紹介記事で、普及率や効果の数値は確認していない。一次資料の整理は [loop-engineering-research.md](loop-engineering-research.md) を参照する。

## 現状

| 部分 | いまの形 |
|---|---|
| 作成ダイアログ（`ui/task-quick-add.js`） | タイトル（必須）、説明（任意）、列・カテゴリ、「整理の詳細」 |
| 作成 API（`canban_create_task` → `store.createTask`） | title, description, list, directory, labels, context, sourceContext |
| 改善ループ（`server/loop.mjs`） | `configure` で目標・条件（1〜20、文字列）・守る原則・周回上限（1〜20、既定 5）。開始・観測・停止・版を管理 |
| カードの表面（`ui/card-face.js` `faceTaskNow`） | ループがあれば「周回 n/m · 状態 · 前回の確認」 |
| 既定の列 | 受信箱 / 進行中 / レビュー / 完了（列は利用者が編集できる） |

改善ループはタスクを作った**後**にカード内で設定する別の操作になっている。この設計では同じデータを作成時に書かせる。新しい保存形式は最小限にする。

## B. 任せる度合い

| 度合い | 意味 | 必須 | 推奨 | 作成時に作るもの |
|---|---|---|---|---|
| **L0 メモ** | あとで考える。エージェントには渡さない | タイトル | — | タスクカードのみ（現状と同じ） |
| **L1 1回の依頼** | 1回の依頼で終わる。人が結果を見る | タイトル、目標 | 完了の条件 | タスクカード（条件があればループも設定） |
| **L2 ゴールのループ** | 条件を満たすまで周回させる | タイトル、目標、完了の条件 1件以上、各条件の確かめ方、周回上限 | 範囲・触らないもの、関門、時間の上限 | タスクカード＋大きなループ（`configure` 済み、状態 `ready`） |
| L3（予約） | グラフに分けて並行させる（E） | — | — | 今回は選べない。表示もしない |

- 既定は **L1**。目標はタイトルから下書きし、そのまま `⌘/Ctrl+Enter` で作れる。従来どおり1欄で作れる速さを残す。
- 前回選んだ度合いを、作成元のレーンごとに共有 UI 状態へ覚える（`creationLevelByLane`）。
- 既存のカードと、度合いを持たないカードは L0 として扱い、警告を出さない。
- 度合いはあとからカードの属性の1行で変えられる。上げると、足りない項目が準備度に現れる。

## A. ゴールの契約

### 項目

| 項目 | 保存先 | 制約 | 案内 |
|---|---|---|---|
| 目標 | `loop.cycles[大].goal` | 1〜500字 | 「なぜ・何を」を1文で。タイトルから下書き |
| 完了の条件 | `loop.cycles[大].criteria[].text` | 1〜20件、各500字 | 確かめられない言葉を警告（後述） |
| 確かめ方 | `criteria[].verify`（**新規・任意**） | `{ kind, value }` | 条件ごとにチップで選ぶ |
| 範囲・触らないもの | `loop.cycles[大].principles` | 4000字 | 「触らない: …」「守る: …」の例を出す |
| 周回上限 | `loop.cycles[大].maxRounds` | 1〜20、既定 5 | 数字の段階入力 |
| 時間の上限 | `task.contract.timeLimitMin`（**新規**） | 5〜1440分、任意 | 今回は表示と指示文への記載のみ。強制はしない |
| 関門 | `task.contract.gates`（**新規**） | `merge` / `production` / `cost` / 自由記述 1件 | 指示文に「この前に止まって人に確認する」として載せる |

確かめ方の種類:

| kind | value | 例 |
|---|---|---|
| `command` | コマンド文字列 | `npm test` が 0 で終わる |
| `ci` | チェック名 | `test (ubuntu)` が成功 |
| `ui` | 画面と操作 | ボードで `c` → 作成 → カードが受信箱に出る |
| `human` | 確認する人・観点 | 文言を人が読む |

`verify` は記録と指示文のためのもの。Canban はこのコマンドを実行しない（検証の自動化は [loop-engineering-plan.md](loop-engineering-plan.md) の「今後」）。画面にも「エージェントに伝える確かめ方」と書き、「自動で検証」とは書かない。

### 確かめられない条件の警告

ローカルの規則だけで判定する（LLM は使わない）。作成は止めず、条件の行の下に警告と書き換えの例を出す。

- 警告する語: 良く・きれい・適切・改善・最適・ちゃんと・なるべく・使いやすい・問題ない・しっかり、数値のない「速く/軽く/高速化」
- 確かめられる兆し（警告を消す）: 数値＋単位、バッククォートのコマンド、「が通る」「が 0 で終わる」「と表示される」「を返す」「が存在しない」、`verify` が設定済み
- 例の表示: 「速くする」→「一覧の初回表示が 200ms 以内（`npm run bench:board`）」

判定は `ui/task-contract-model.js` の純関数とし、サーバーも同じ規則で準備度を計算する（警告は準備度の不足には数えない。L2 では `verify` のない条件を不足に数える）。

### データの変更

```
task.contract = {            // 新規。度合いのないカードには付けない
  level: 0 | 1 | 2,
  timeLimitMin?: number,
  gates?: ('merge' | 'production' | 'cost' | { text: string })[],
  overrides?: [{ at, by: 'human', missing: string[], to: listId }]   // C の上書き記録（最新 20 件）
}
loop.cycles[].criteria[] = { id, text, verify?: { kind, value } }    // verify を追加
```

- `criteria` の入力は従来の文字列も受け付ける（`{ text }` に正規化）。既存の `definitions` の版は書き換えない。
- `loopPrompt`（`server/loop.mjs`）は、条件の後に「確かめ方」、原則の後に「止まって人に確認する関門」と「時間の上限」を載せる。

### 作成の原子性

`createTask` に `contract` 引数（`{ level, goal, criteria, principles, maxRounds, timeLimitMin, gates }`）を足す。カードの作成と大きなループの `configure` を **同じ `mutate`** の中で行い、途中で失敗したら両方とも作らない。`clientRequestId` の重複送信では既存のカードを返す。ループの `configure` の検証は `loop.mjs` から関数として取り出して共用し、二重に実装しない。

`canban_create_task` の入力スキーマにも `contract` を足す。エージェントが MCP で作るタスクも同じ契約を持てる。

## C. 着手の準備度

### 計算

`contractReadiness(card) → { level, required: n, filled: m, missing: ['goal' | 'criteria' | 'verify:c2' | 'maxRounds' …], warnings: [...] }`。保存しない。カードの状態から毎回計算する（寿命の段階と同じ扱い）。

### 表示

| 場所 | 表示 |
|---|---|
| カードの表面 | L1 以上で不足があれば、`faceTaskNow` の行を「契約 3/5 · 確かめ方が未設定」に置き換える。満たしたら従来の周回表示に戻す |
| カード詳細の属性の1行 | 度合いのチップ（`L2 ゴールのループ`）。押すと度合いを変えるポップオーバー（レイヤー4） |
| 改善ループの部品 | 不足している項目へフォーカスを移す「契約を埋める」 |

### 着手の関門

着手とみなす操作と、そのときの扱い:

| 操作 | 対象 | 扱い |
|---|---|---|
| 人が「着手の関門あり」の列へ移す（ドラッグ / カード詳細） | L1 以上で不足あり | 確認ダイアログ（レイヤー3）に不足を列挙。「契約を書く」（既定）/「このまま移す」。後者は `contract.overrides` に記録 |
| エージェントが MCP で同じ列へ移す | L1 以上で不足あり | 拒否し、不足をエラーで返す。上書きはできない |
| 周回の開始・`canban_send_loop` | L2 で不足あり | サーバーで拒否（既存の UI トークン境界はそのまま） |
| タスクから「新しいセッションを開始」 | L1 以上で不足あり | 入力欄の上に不足を示すが止めない（人が対話で始める操作のため） |

- 列に `requiresContract: boolean` を足す。**新しいボードでは「進行中」を true**、既存のボードは false のままにし、リストメニューの「着手の関門」で切り替える。列の意味を Canban が決めつけないため。
- L0 のカードは関門の対象外。
- 現在はボードのドラッグ（`ui/drag.js`）、カード詳細（`ui/card-overlay.js`）、エージェントの MCP 呼び出しが同じ `canban_move_card` を使い、呼び出し元を区別できない。そこで `canban_move_card` は不足があれば常に拒否し、不足の一覧を返す。「このまま移す」は UI 専用の `canban_move_card_override`（`uiToken` 必須、改善ループの確認と同じ `requireLoopUi` の境界）で行う。この境界は UI 経路の確認であり、本人の認証ではない（[loop-engineering-plan.md](loop-engineering-plan.md) と同じ注意）。

## UI（作成ダイアログ）

レイヤー3の既存のダイアログの「タスクカード」の中身だけを変える。新しい入口・ページ・キーの予約は足さない。

```
┌ 作成 ───────────────────────────────────────── Esc ┐
│ [タスクカード] [今すぐ始める]                            │
│ 任せる度合い  ( L0 メモ | ●L1 1回の依頼 | L2 ゴールのループ ) │
│ タイトル      [リリースの準備をする                    ]  │
│ 目標          [0.30 をストアに出せる状態にする          ]  │
│ 完了の条件    1 [npm test が 0 で終わる     ] [command ▾] │
│              2 [ストア審査用の画像が揃う     ] [human  ▾] │
│              ＋ 条件を追加                                │
│   ⚠ 「きれいに」は確かめられません。例: …                    │
│ ▸ 範囲と予算（周回 5 · 時間 — · 関門 マージ前）            │
│ 列 [受信箱▾]  カテゴリ [—▾]   ▸ 整理の詳細               │
│ 契約 4/5 · 確かめ方が1件未設定      [タスクを作成 ⌘Enter] │
└────────────────────────────────────────────────────┘
```

- 度合いは `radiogroup`。矢印キーで切り替え、度合いに合わない欄は畳む（値は下書きに残す）。
- 条件の行では `Enter` で次の行を足す（IME の変換中は無視、既存の `isComposing` の扱いと同じ）。`⌘/Ctrl+Enter` は作成。
- 「範囲と予算」は `details`。L2 では開いた状態で始める。
- 下端に準備度を出す。L2 で不足があっても作成はできる（作るのは止めず、着手で止める）。ボタンの文言は「タスクを作成（契約 4/5）」とし、不足を隠さない。
- 下書きは既存どおり種類ごとに保持し、条件の配列も含める。Slack からの作成では L0 を既定にする。

用語: 「任せる度合い」「ゴールの契約」「完了の条件」「確かめ方」「関門」。実装時にまず [ui-components.md](ui-components.md) の「作成ダイアログ」に追記してから部品を作る。

## 実装の分け方

| PR | 内容 | 確認 |
|---|---|---|
| 1. モデルとサーバー | `task-contract-model.js`（準備度・警告）、`criteria[].verify`、`createTask` の `contract` と原子的な `configure`、指示文の追記、MCP の拒否 | 単体試験: 準備度、警告の判定表、作成の巻き戻し、重複送信、旧形式の条件、エージェントの移動拒否 |
| 2. 作成ダイアログ | 度合い、条件の行、警告、範囲と予算、準備度の表示、下書き | dev ホストでアプリ内ブラウザ確認（キーボードだけで L2 を作る、IME、狭い幅、ダーク） |
| 3. 表面と関門 | カード表面の契約表示、属性の1行の度合い、列の `requiresContract`、移動の確認ダイアログと上書き記録 | 単体試験＋ブラウザ確認。ボード描画のベンチが予算内であること |

各 PR で CHANGELOG と `ui-components.md` を更新する。

## 決めていないこと

1. 「進行中」への関門を、新しいボードの既定で有効にするか（本書の案は有効）。
2. L1 の既定を全レーン共通にするか、レーンごとに覚えるか（本書の案はレーンごと）。
3. 時間の上限を、検証の自動化より前に強制するか（本書の案は表示のみ）。
